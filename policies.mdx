title: "Policies"
---

OuterProduct uses [Cedar](https://www.cedarpolicy.com/) for policy management. Cedar is an authorization language that describes who may perform which actions on which resources. 

A basic Cedar policy has three parts, such as the following policy which permits one user to read one volume:

```text
permit (
    principal == User::"users/01234567-89ab-cdef-0123-456789abcdef",
    action == Action::"volume_read",
    resource == Volume::"volumes/fedcba98-7654-3210-fedc-ba9876543210"
);
```

## Key concepts

### Principal

The **principal** is the identity attempting an action, typically the authenticated user making the request. OuterProduct users have canonical identifiers such as:

```text
User::"users/01234567-89ab-cdef-0123-456789abcdef"
```

A user can also be a member of one or more groups. A policy can grant access through group membership:

```text
principal in Group::"groups/analytics"
```

### Action

An **action** is the operation the principal wants to perform. Examples include:

```text
Action::"volume_read"
Action::"volume_write"
Action::"secret_use"
Action::"execute_run"
```

Actions are specific to a resource type. For example, `volume_write` applies to volumes, while `execute_run` applies to runs.

### Resource

The **resource** is the object on which the action is attempted, such as a volume, secret, run, user, or group. Resources use typed canonical identifiers:

```text
Volume::"volumes/fedcba98-7654-3210-fedc-ba9876543210"
Secret::"secrets/01234567-89ab-cdef-0123-456789abcdef"
Account::"account"
```

### Policy

A **policy** is a rule that either permits or forbids access. The rule contains:

- An **effect**: `permit` (to grant access) or `forbid` (to deny access)
- A **principal** constraint
- An **action** constraint
- A **resource** constraint
- Optionally, a `when` or `unless` condition

A matching `forbid` overrides every matching `permit`.

### Conditions

A policy can use a `when` condition to apply only when an additional expression is true:

```text
permit (
    principal is User,
    action == Action::"volume_read",
    resource is Volume
)
when {
    resource has created_by &&
    resource.created_by == principal
};
```

An `unless` condition has the inverse meaning: the policy applies unless the expression is true.

## Creating a policy

### Using the visual builder

The visual builder is the simplest way to create a policy. It generates Cedar based on the selections you make. To create a policy, open **Policies** in the dashboard and:

1. Select **New policy**.
2. Choose the principals to which the policy applies. A policy can apply to one specific user, a selected set of users, or all users. 
3. Choose a resource type and one or more actions. The builder offers convenient presets for Read only, Contributor, and Full access.
4. Select whether the policy allows or denies those actions. Note that a matching deny overrides access granted by any other policy.
5. Choose one resource or all resources of that type.
6. Review the generated Cedar and save the policy.

### Writing Cedar directly

Select the **Cedar** editor when you need more control than the visual builder provides.

The Cedar editor is useful for:

- Granting access through group membership
- Writing additional `when` or `unless` conditions
- Combining several principal or resource conditions
- Creating narrowly tailored deny rules
- Reviewing or editing the exact policy source

For example, the following policy gives members of the analytics group read access to one volume:

```text
permit (
    principal in Group::"groups/analytics",
    action == Action::"volume_read",
    resource == Volume::"volumes/fedcba98-7654-3210-fedc-ba9876543210"
);
```

Multiple actions can be included in one policy:

```text
permit (
    principal in Group::"groups/analytics",
    action in [
        Action::"volume_read",
        Action::"volume_write"
    ],
    resource == Volume::"volumes/fedcba98-7654-3210-fedc-ba9876543210"
);
```

A type-wide policy can cover every resource of that type:

```text
permit (
    principal in Group::"groups/data-science",
    action == Action::"execute_run",
    resource is Run
);
```

Each policy saved through the dashboard contains one Cedar statement. Create additional policies when separate rules are easier to understand or manage.

When an existing policy is opened, it is shown in the Cedar editor. Switching from Cedar back to the visual builder starts a new visual policy and replaces the current Cedar draft after confirmation.

### Creating policies through the API

Policies can also be created, updated, listed, and deleted through the Policy API. This is useful when policies are managed through automation or an infrastructure workflow.

An API-created policy contains the same fields as a dashboard policy:

- An optional display name
- An optional description
- A required Cedar statement
- A server-assigned policy identifier
- An ETag used to protect updates from concurrent changes

Policies created through the API use the same validation and authorization rules as policies created in the dashboard.

## Available actions

The current policy model includes the following major resource-specific actions.

| Resource | Actions |
| :-- | :-- |
| Account | Account administration and creation or listing of top-level resources |
| User | `get_user`, `update_user`, `disable_user`, and API-key actions |
| Group | `get_group`, `update_group`, `delete_group` |
| Policy | `get_policy`, `list_policies`, `create_policy`, `update_policy`, `delete_policy` |
| Volume | `volume_read`, `volume_write`, `volume_manage` |
| Secret | `secret_read`, `secret_manage`, `secret_use` |
| File tree | `read_file_tree`, `use_file_tree`, `delete_file_tree` |
| Run | `read_run`, `execute_run`, `cancel_run`, `delete_run` |

The dashboard shows the exact actions available for the selected resource type.

## How policies are evaluated

When a user attempts an operation, OuterProduct evaluates:

```text
principal + action + resource
```

The decision includes all applicable built-in and user-defined policies.

Access is allowed only when:

1. At least one matching policy permits the request.
2. No matching policy forbids the request.

If no policy permits the request, access is denied. This is known as **default deny**.

For example, suppose one policy grants a group permission to execute runs:

```text
permit (
    principal in Group::"groups/operators",
    action == Action::"execute_run",
    resource is Run
);
```

Another policy forbids execution of one particular run:

```text
forbid (
    principal is User,
    action == Action::"execute_run",
    resource == Run::"runs/fedcba98-7654-3210-fedc-ba9876543210"
);
```

Members of the operators group can execute other runs, but they cannot execute the specifically denied run.

## Built-in access

OuterProduct includes built-in policies for common ownership and self-service behavior. Among other things, these policies allow users to:

- Manage their own user information and API keys
- Create common resources such as volumes, secrets, file trees, and runs
- Access resources they created

Ownership is determined from trusted resource metadata maintained by OuterProduct. A caller cannot claim ownership by supplying a `created_by` value.

Built-in policies are evaluated alongside policies created in the dashboard. They cannot be viewed or edited as ordinary dashboard policies.

## Advanced considerations

### Policies are additive

Creating a new policy does not replace an existing policy. All applicable policies participate in the decision.

Splitting access into several small policies is often easier to understand than creating one large policy. For example, read access and management access can be granted separately.

### Deny rules take precedence

A broadly scoped deny can remove access granted by many other policies. Before saving a deny policy, carefully review:

- Its principal scope
- Its selected actions
- Whether it applies to one resource or an entire resource type

### Broad policies include future resources

A constraint such as:

```text
resource is Volume
```

matches all current and future volumes. Use an exact resource identifier when the grant should apply only to one object.

### Group membership is evaluated at request time

A group policy applies according to the user’s current group membership. Adding or removing a user from a group changes which group policies apply to that user.

### Policy changes take effect immediately

Saved policy changes and deletions affect subsequent authorization checks. A user who has already loaded a page may still see a control that was rendered using an earlier permission check, but the underlying operation performs authorization again.

### Interface permissions are only hints

The dashboard may check permissions to decide whether to display or enable a control. That check does not reserve access or guarantee that the operation will succeed. Every operation is independently authorized when it is performed.

### Policy filtering is not an access explanation

Filtering the policy list by a resource shows policies that target that exact resource. Broader policies—such as policies for all volumes or conditional Cedar policies—may also affect access to it.

The filtered list should therefore not be interpreted as a complete explanation of why access was allowed or denied.

### Managing policies requires permission

Policies are themselves protected resources. A user must have the appropriate policy-management action, such as `create_policy`, `update_policy`, or `delete_policy`, for the policy’s scope.

Editing a policy does not allow a user to expand their own administrative scope. If an edit moves a policy to a new resource scope, the user must also be permitted to create a policy in that new scope.

### Use canonical identifiers

Cedar policies should use the canonical resource identifiers shown by OuterProduct, such as:

```text
User::"users/{uuid}"
Volume::"volumes/{uuid}"
Run::"runs/{uuid}"
Account::"account"
```

Display names are intended for people and may change. Canonical identifiers are the stable values used for authorization.
